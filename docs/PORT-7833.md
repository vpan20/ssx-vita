# The 0.0.7833 adaptation

lukebrl's port targets `ssx-v0_0_8430.apk`. This fork targets `ssx-v0_0_7833.apk` (libgame.so sha256
921bd7a9...), the only copy its author has. The game code is the same engine build family; the binary
differs by small code-size shifts, so every address the port patches moved.

How the offsets were re-resolved (all 132 `OFF_` defines, the literal `hook_addr` sites, the busy-wait
branches, the buffer creator allowlist):

- Function entry points: by symbol name from libgame.so's own symbol table (`nm -C`), 7833 is not stripped.
- Mid-function sites (a `cmp`, a `beq`, a `strb`, a literal): located by instruction pattern inside the
  named function; in every case checked the intra-function offset was identical to 8430's.
- Data: the GameRender* GOT entry from FileRef::Unload's `ldr r0,[pc,rX]`; the attribute name table and
  "OGLESRnaAttribute" by string search; FEDataStore's instance = `System::Singleton<FEDataStore>::sInstance`.
- Every patch keeps lukebrl's instruction checks, so a wrong address logs `[MODULE] ... not as expected` and
  leaves that patch off instead of corrupting the game.

Known differences in 7833:
- MERCURY (the DLC downloader) is not linked into libgame.so (it ships as a separate `libmercury.so` the
  game never loads here), so its init hook is gone.
- `ProcessFEPostRaceProgression` waits on front-end flag 197 (200 in 8430): same patch, different id.
- `WorldResourceAllocator::CreateGameObject` has a fourth vertex-buffer creator; it is not in the allowlist
  (8430's list has three), matching lukebrl's choice of what is safe to free.
